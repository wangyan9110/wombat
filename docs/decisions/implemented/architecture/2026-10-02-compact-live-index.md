# 决策记录：紧凑实时索引与替换算法

中文 | [English](2026-10-02-compact-live-index.en.md)

Status: implemented

## 问题

旧索引每条安全事实重复保存scope文本及JSON编码的字段/身份键；解析候选与提交投影均需要恢复，重复键开销随记录数增长。整字段替换构造完整编码键集合、再复制全部旧键；初次大事务留下的WAL文件也可能在后续小追加中维持峰值大小。

## 决定

live-v1目录内的SQLite独立使用user_version=2。buckets字典按(scope,field)唯一分配整数；entries使用(bucket,id)复合主键和WITHOUT ROWID，每条事实不再重复范围/字段文本或JSON键。载荷通过SQLite自身jsonb编码、json解码，作为数据库内部不透明BLOB；公共DTO、快照v1/v2/v3和来源适配版本不变化。JSONB是体积优化，不声称字段访问为常量时间，见[SQLite官方说明](https://www.sqlite.org/json1.html#jsonb)。

字段替换使用借用身份的HashSet，逐行查询现有身份，只复制需删除的身份，完成读取后才删除。不一边扫描同表一边修改；相同载荷不重写。追加仍仅写脏计量、操作和游标，不改为逐次VACUUM或整库重写。

不可变计价事实回灌解析缓存时，三个身份有序序列采用归并游标，先检查共享指针、仅在值相等时复用。替代逐行BTreeMap查找和投影二分搜索，单来源额外工作为线性遍历且不分配新集合；不同值的更正、缺失身份和其他来源不覆盖。多来源仍分别经过全局计量序列，不宣称局部追加已与全历史规模无关。

每连接设置4MiB页缓存目标、文件临时存储、512页自动检查点和8MiB日志保留目标；保持WAL、FULL同步和原提交事务。日志目标不是硬空间上限：大事务、活跃读者和检查点失败可能暂时扩大WAL。页缓存预算也不是进程峰值内存上限，内存事实/版本另有成本。

旧kv索引按行在IMMEDIATE事务中迁移，检查旧键、转换载荷；任何错误回滚旧表，提交后才执行一次VACUUM回收旧布局空页。迁移可能需要额外磁盘、时间及写锁；压实失败不损坏已提交的新索引。未知schema版本明确拒绝，不删除数据。不可重建的user-v1处理记录、配置缓存和不可变快照不参与迁移。旧程序不能继续写新布局，正常重启宿主后使用新内核。

## 考虑过的方案

继续使用文本kv并仅限制WAL只能减少日志保留，无法消除逐行重复键。为每个小记录引入通用压缩会增加编解码成本与依赖，本次先复用已锁定SQLite。完整数据库聚合、候选/投影进一步共享以及快照内容寻址能继续降低资源，但影响累计撤销、固定版本和文件快照兼容，本次不一次重写这些边界。

## 影响与验证

回归覆盖旧布局迁移/重启、最大整数和极小浮点值、Unicode/转义、损坏迁移事务回滚、未来版本拒绝、空映射/标量、字段/来源隔离、替换删除、相同值不写和损坏载荷报错。CLI端到端将真实合成索引转为旧布局，再验证缓存版本、游标追加、固定查询和快照导出。

release固定语料分别记录冷/热查询、追加、峰值RSS、数据库/WAL及闲置退出后磁盘；结果与限制见[进度](../../../project/progress.md)。事实仍有候选/投影两份持久表示，内存仍按历史规模增长；百万级、长期驻留、其他平台和真实来源未因此完成验收。
